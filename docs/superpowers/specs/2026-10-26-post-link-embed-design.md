# 게시글 내 영상 링크 자동 임베드 설계 문서

- 날짜: 2026-10-26
- 상태: 설계 승인됨 → 구현 진행
- 관련 코드: `src/app/board/[category]/[postId]/page.tsx`(게시글 상세 렌더링),
  `src/lib/types.ts`, `next.config.ts`

## 배경 / 목적

봇 계정으로 틱톡/페이스북 영상 링크가 포함된 글을 올리려다, 지금 게시글 본문이
순수 텍스트(`whitespace-pre-wrap`)로만 렌더링돼서 `<iframe>` 코드를 그대로
붙여도 글자 그대로만 보이고 재생되지 않는다는 걸 확인했다. 대화를 통해
"다른 사이트들처럼, 회원이 올린 글에 지원 플랫폼 링크가 있으면 자동으로
재생 가능한 형태로 보여주자"는 방향으로 정리됐다.

대화를 통해 정리된 핵심 방향:
1. **봇 글만이 아니라 일반 회원 글에도 적용한다.** 그래서 보안을 "봇만 믿는"
   수준이 아니라 "임의의 회원이 악의적으로 입력해도 안전한" 수준으로 다룬다.
2. **서버가 사용자 입력에 기반해 외부 URL을 호출하지 않는다(SSRF 회피).**
   oEmbed API를 실시간으로 호출하는 대신, 지원 플랫폼의 "시청 URL" 형태를
   정규식으로 엄격히 검증하고, 거기서 뽑아낸 ID로 **우리가 직접** 알려진
   임베드 URL 템플릿을 조립한다. 외부가 돌려주는 HTML 문자열은 절대 신뢰하지
   않는다(`dangerouslySetInnerHTML` 사용 안 함 — 항상 React JSX로 직접
   `<iframe src=...>`를 만든다).
3. **플랫폼 범위는 다시 좁혔다.** 처음엔 유튜브/틱톡/X를 모두 "링크 → iframe"
   패턴으로 묶어서 생각했는데, 확인해보니 X(트위터)의 공식 임베드는
   `<blockquote>` + 외부 스크립트(`platform.twitter.com/widgets.js`)를 우리
   페이지에서 실행시키는 방식이라 "우리가 만든 고정 틀의 iframe만 신뢰한다"는
   이번 설계 원칙과 안 맞는다. **이번 1차 범위는 유튜브·틱톡 두 개로 한정**하고,
   X는 별도 설계가 필요한 건으로 제외한다. 페이스북·인스타그램은 메타 개발자
   앱 등록 + 앱 심사가 필요해 더 무거운 별도 작업이라 처음부터 범위 밖이다
   (이 두 플랫폼 링크는 지금처럼 평문 텍스트로만 남는다 — 동작 변화 없음).
4. **모바일 데이터 비용을 고려해 자동재생은 기본 끈다.** 이 사이트 사용자층이
   외국인 노동자 등 모바일 데이터 비용에 민감할 수 있는 계층이라는 점을
   반영한다.
5. DB 스키마 변경 없음 — 렌더링 시점에 `post.body` 텍스트를 스캔해서 처리하는
   순수 프론트엔드 기능이다. 글 작성 화면(`write/page.tsx`)의 `<textarea>`는
   변경하지 않는다.

## 범위

**포함**

1. **URL 인식 유틸** `src/lib/embeds.ts` (신규)
   - 플랫폼별 정확 매칭 정규식 (scheme은 `https`만 허용, 호스트는 정확히
     아래 목록과 매치, 불필요한 쿼리/유저인포 포함된 변형은 매치 실패 처리):
     - YouTube: `^https:\/\/(www\.)?youtube\.com\/watch\?v=([\w-]{11})(&.*)?$`,
       `^https:\/\/youtu\.be\/([\w-]{11})(\?.*)?$`,
       `^https:\/\/(www\.)?youtube\.com\/shorts\/([\w-]{11})(\?.*)?$`
     - TikTok: `^https:\/\/(www\.)?tiktok\.com\/@[\w.-]{1,24}\/video\/(\d{5,25})(\?.*)?$`
       (단축링크 `vm.tiktok.com`은 리다이렉트 해석이 필요해 1차 범위 제외 —
       전체 형태 watch URL만 인식)
   - 매치되면 `{ provider: "youtube" | "tiktok", embedUrl: string }`을 반환.
     `embedUrl`은 추출한 ID로 우리가 직접 조립:
     - YouTube: `https://www.youtube-nocookie.com/embed/<id>?autoplay=0&rel=0`
       (프라이버시 강화 도메인 사용 — 시청 전까지 유튜브 쿠키 안 심음)
     - TikTok: `https://www.tiktok.com/player/v1/<id>?autoplay=0&music_info=0&description=0`
   - 매치 안 되면 `null` 반환 — 호출부는 원래 텍스트를 그대로 둔다.

2. **렌더링** `PostBody` 컴포넌트(신규)
   - **적용 범위**: `[postId]/page.tsx`에는 `whitespace-pre-wrap` 블록이 3곳
     있는데(뉴스 원문 발췌 / 뉴스 한국어 요약 / 뉴스 아닌 일반 카테고리 본문),
     이 기능은 **일반 카테고리 본문(227번 줄, 뉴스가 아닌 모든 카테고리가
     쓰는 분기)에만** 적용한다. 뉴스 글은 운영자 전용 파이프라인
     (`publish-news.mjs`)으로만 올라가고 봇도 뉴스 카테고리엔 못 쓰므로
     이번 기능의 동기(회원·봇이 올린 글의 링크)와 무관하다. 뉴스 쪽 두
     블록은 건드리지 않는다.
   - **번역 토글과의 관계**: 임베드 감지는 항상 **원문 `post.body`를
     기준으로만** 동작한다(번역 API가 돌려주는 `translated.body`는 절대
     스캔하지 않음). 이유: 번역은 사람이 읽는 문장을 위한 것이지 URL
     구조를 보존할 의무가 없어서, 번역된 텍스트를 기준으로 정규식을
     매칭하면 줄바꿈/공백이 미묘하게 바뀌어 번역 토글을 켤 때마다 임베드가
     사라지는 식으로 깨질 수 있다. 그래서 "번역 보기"를 켜고 끄는 것과
     무관하게 임베드 박스는 항상 그대로 떠 있고, 그 위의 본문 텍스트만
     기존처럼 원문/번역이 토글된다.
   - `post.body`를 줄바꿈 기준으로 스캔하면서 각 줄(또는 줄 내 URL 토큰)이
     위 유틸에 매치되는지 확인.
   - 매치된 URL은 **텍스트 자리에 그대로 두되, 그 아래에 임베드 박스를 추가로
     렌더링**한다(링크 텍스트 자체를 지우지 않음 — 원문 보존, 임베드가 깨져도
     사용자가 링크를 읽고 직접 이동할 수 있게).
   - 글 하나에 **최대 3개**까지만 임베드 렌더링(그 이상은 텍스트로만 유지) —
     스팸성 글이 페이지를 무겁게 만드는 것 방지. 상수명은 구현 시 정한다.
   - 임베드 박스 `<iframe>` 속성(고정값, 사용자 입력 전혀 개입 안 함):
     - `src`: 위에서 조립한 `embedUrl`
     - `sandbox="allow-scripts allow-same-origin allow-popups allow-presentation"`
       — 주의: `allow-same-origin`을 같이 주는 게 일반적으로는 위험하지만,
       여기서는 iframe의 출처(youtube-nocookie.com / tiktok.com)가 우리
       사이트와 절대 같을 수 없도록 호스트를 고정 템플릿으로만 조립하므로
       "프레임이 자기 sandbox를 해제하고 부모 페이지에 접근" 시나리오가
       성립하지 않는다. 대신 유튜브/틱톡 플레이어가 정상 작동하려면(자체
       쿠키/localStorage 접근) 이 속성이 필요하다. 반대로 사용자가 입력한
       임의 URL을 그대로 쓰는 구조였다면 반드시 빼야 하는 속성이었을 것 —
       이 설계가 "URL을 직접 조립"하는 방식이라 가능한 선택이다.
     - `allow="encrypted-media; picture-in-picture; fullscreen"` (autoplay는
       명시적으로 제외)
     - `loading="lazy"`, `referrerpolicy="strict-origin-when-cross-origin"`
     - `title`은 플랫폼명만("YouTube 영상" 등, 실제 영상 제목은 안 가져옴 —
       oEmbed 호출 자체를 안 하므로 제목/작성자 메타데이터 없음, 이번 범위
       밖)
   - 고정 비율 반응형 박스(16:9 등 플랫폼별)로 감싸서 레이아웃 흔들림 방지.

3. **CSP 헤더 추가** (`next.config.ts`) — 심층방어 차원에서 사이트 전역에
   `Content-Security-Policy: frame-src 'self' https://www.youtube-nocookie.com https://www.tiktok.com;`
   추가. sandbox 속성이 1차 방어선이고 이건 2차 방어선(혹시 다른 경로로
   임의 iframe이 섞여 들어가도 브라우저가 차단).

**제외 (YAGNI / 이번 범위 아님)**

- X(트위터) 임베드 — 공식 임베드가 외부 스크립트 실행 방식이라 이번 설계
  원칙과 안 맞음. 별도 설계 필요(스크립트를 신뢰할지, 아니면 비공식
  `platform.twitter.com/embed/Tweet.html?id=...` iframe을 쓸지 등 검토 필요).
- 페이스북 · 인스타그램 — 메타 개발자 앱 등록 + 앱 심사 필요, 별도 작업.
- 틱톡 단축링크(`vm.tiktok.com/...`) 해석 — 리다이렉트 추적이 필요해 SSRF
  표면을 다시 넓히므로 1차 제외. 사용자는 틱톡 앱의 "링크 복사"가 아니라
  브라우저 주소창의 전체 URL을 써야 임베드됨 (안 되면 텍스트 링크로만 남음,
  동작 깨지지 않음).
- oEmbed로 제목/작성자/썸네일 등 메타데이터 가져오기 — 이번엔 안 함(서버
  외부 호출 자체가 없는 게 핵심 설계 포인트라, 메타데이터가 꼭 필요해지면
  그건 그 자체로 SSRF 방지책을 다시 설계해야 하는 별도 작업).
- 글쓰기 화면에서 "미리보기" 표시 — 이번엔 상세화면 렌더링에서만 동작.
- 댓글 본문에서의 임베드 — 이번 범위는 게시글 본문(`posts.body`)만, 댓글
  (`CommentSection.tsx`)은 제외.

## 내 판단으로 결정한 것(builder's call)

- 정규식 그룹 캡처 등 정확한 구현 디테일, 반응형 박스의 정확한 Tailwind
  클래스는 구현 시점에 정한다.
- 글당 임베드 최대 개수(3개) 값 자체는 builder's call — 필요시 나중에
  조정 가능한 상수로 분리.
- `sandbox`/`allow` 속성 조합은 위 문서의 추천값으로 시작하되, 실제 유튜브
  nocookie / 틱톡 플레이어 임베드로 수동 테스트해서 깨지는 기능이 있으면
  최소 권한 원칙 안에서 조정한다.
- CSP `frame-src` 헤더는 기존 `next.config.ts`에 다른 보안 헤더가 전혀
  없는 상태라 이번에 처음 추가하는 것 — 다른 보안 헤더(X-Frame-Options 등)
  전반을 손보는 건 이번 범위 밖이므로 `frame-src`만 추가한다.
